# Changelog

All notable changes to glint are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow semver, where before 1.0 a minor bump may break things.

## [Unreleased]

### Added

- **`wait_for_settle` takes `timeoutMs`.** It is an alias for `ceilingMs`, named as in `wait_for`, so an agent that guesses the `wait_for` name no longer needs a second call. (#274)
- **The server instructions suggest a subagent for long runs.** Every glint call re-reads the caller's whole conversation, so a long UI-driving run in a large conversation costs that conversation many times over. The workflow section now says to hand the driving to a subagent with a self-contained brief and keep irreversible steps in the main agent. Two examples that repeated the gotchas paid for the line. (#276)
- **`app_logs` can search.** `contains:"EventTracker"` keeps entries with that text (case-insensitive) and `match:"<regex>"` keeps entries matching a Dart regex (an invalid one is an `invalidArgument` with the regex error); both filters apply before `limit`, so `limit:20 contains:"X"` returns the last 20 matching entries, and the reply opens with `3 of 412 entries matched "EventTracker"`. Each entry is cut at `maxChars` (default 600, `0` for whole entries) with a marker naming how many chars were dropped, and a reply that is still huge keeps the newest entries under about 20000 chars; `seq` stays on every entry and `nextSequence` still advances past everything scanned. (#270)
- **Log breakpoints.** `breakpoint op:set pattern:"<regex>"` pauses the app the moment it logs a matching line (print, debugPrint, `developer.log` or stderr), screenshots that screen, and holds it until `breakpoint op:resume`. `op:wait` blocks until the next hit, with progress every 15 s; `op:status`, `op:list` and `op:clear` manage the rest. `pause:false` records hits without pausing. While paused, scene reads say which breakpoint holds the app instead of reporting a generic unresponsive app, `hot_reload` refuses while the app is paused, and glint resumes a paused app when it detaches.
- **Drive a route like a person.** `location op:route maxSpeedKmh:90` varies the speed between `speedKmh` and `maxSpeedKmh` the way a driver does: it accelerates and brakes smoothly, slows before bends and comes to a stop at the end, so testing an app against real driving no longer needs a constant-speed GPX. `slowForTurns:false` skips the braking for bends. The reply lists the cruise range and how many turns it brakes for, and `op:get` reports the current speed.

### Fixed

- **Several agents sharing one glint no longer land on each other's apps.** Each call named its app by swapping a field shared by every call in flight, so a `scroll_to_find app:"<udid>"`, or a `record` whose steps did not repeat `app`, could read another agent's app halfway through. The app a call names is now bound to that call alone (and to the tools and steps it runs inside it), and the shared active app only applies to calls that name none. (#279)
- **`app_logs` kept its entries when the same app is attached again.** Detaching or switching modes (`mode:"device"` then back) threw the log buffer away even though the app process had not restarted. glint now keeps the buffers of the last few detached apps and hands the old one back when the same VM service is attached again, so entries and `nextSequence` carry on. When the app really was a new process, `attach` warns that the earlier entries are gone. (#277)
- **On the iOS simulator, a system alert over the app no longer swallows taps, and a busy app is no longer called new.** An "Allow Paste" or location prompt, a "Camera not available" alert or the photo picker often holds the app's main thread, so `input:auto` taps went to the app, timed out after 10 s and reported "was not delivered". With the XCUITest runner (`iosBackend:"xctest"`), glint now asks it what covers the app (system alerts first, since that read never waits on a blocked app; free from the background poll, re-read only when something is up or the app stops answering) and sends taps, long presses, swipes and typing through the device when a system surface is in front. An in-app input that timed out is never resent natively unless the runner positively sees a system surface, and the app drops any input it only gets to after glint gave up on it, so nothing lands twice (the in-app agent is now `ext.flutter.glintAgent8`). When the VM is only slow (a heavy screen build), the reply is the new `appBusy` errorKind with the timeout and next steps instead of "it has not drawn its first frame", which is now said only for an app that never drew one; `awaitReady`, batch steps, text targets and `wait_for` keep polling through a busy app within their budget. (#265, #258, #257, #255)
- **`attach launch:` named the real reason when `flutter run` failed.** The error used to open with whatever line came last, such as Xcode's `Linker command failed` or Gradle's `BUILD FAILED in 9s`. It now picks the root cause: the first Xcode error (`Library 'c++' not found`), the line under Gradle's `What went wrong`, a Dart compile error with its file and line, or an adb `INSTALL_FAILED_` code. A launch that times out includes the reason too.
- **Coordinates are logical points everywhere, and a point off the screen is refused (#272).** Replies used to mix units: `tap` by glintId said `at (603, 2448) px` while `tap`, `long_press`, `swipe` and `drag` take logical points, so an agent that copied pixels into `swipe` got a silent `changed:false`. Summaries now give logical points (`pt`), `data` adds `logicalCenter` beside `physicalCenter`, and `resolve` reports its centre in points. `tap`, `long_press`, `pinch`, `swipe`, `drag` and `tap sequence` with x,y now fail as `invalidArgument` when a coordinate lies off the screen, naming the coordinate, the screen size, the unit (points, or screenshot pixels in device mode) and the value to use if it was pixels.
- **`swipe` and `drag` report a scroll, and `scroll_to_find` no longer counts a row hidden under a pinned header (#259).** A coordinate `swipe` or `drag` over a scrollable now reads the scroll offset the way `scroll` does, so a page that moved reports `changeCategory:scrolled` with `scrolledPx` instead of `nothing changed`. A row whose centre sits under a pinned header (`SliverAppBar`, pinned `SliverPersistentHeader`) used to count as on screen, because the scroll viewport spans the whole screen: `scroll_to_find` returned it after 0 scrolls while it was out of sight. The visible part of a scroll view now excludes the strip pinned slivers cover, so that row is scrolled into view first.

## [0.5.0] - 2026-10-19

### Added

- **Touches drawn onto recordings.** `record touches:true` also writes `video-touches.mp4` with every touch glint sent drawn on it (the same dot, trail and release ring), on any target and over native surfaces too, because the dots come from glint's own log of what it sent, not from the screen. The frames returned to the agent stay clean. glint notes each touch where it is actually sent, through the app or the device, so the dots line up with the video; drawing uses AVFoundation in glint's macOS bridge (`glint-iossim overlay-touches`), rendered at a steady 30 fps because simulator recordings only hold a frame when the screen changes.
- **Touches drawn system-wide on an Android emulator.** With `showTouches` on, glint's real touches on an emulator go through the emulator's own touchscreen and Android's `show_touches` is switched on, so Android draws each one everywhere: over permission dialogs and the notification shade, on other apps, and in `screenrecord`. glint's in-app overlay then draws only the touches it sends inside the app, so nothing is drawn twice. The setting goes back to what it was when touches are turned off or glint detaches, and a glint that exited without detaching puts it back at the next attach. As a bonus, `pinch` now works through the device on an emulator (two real fingers). `attach` says where touches show (`touches: shown everywhere …`), with `data.touches.system`.
- **See every touch glint makes.** `attach showTouches:true`, or `config op:set key:showTouches value:true` mid-session, draws each touch inside the app: a white dot with a Flutter-blue ring while the finger is down, a short trail behind a swipe or drag, and a ring that fades out on release. Anyone watching the simulator sees it, and so does a screen recording (`record`, `xcrun simctl io recordVideo`). It shows glint's in-app taps, its real device touches and your own clicks in the Simulator alike. The dots are painted over the app through Flutter's debug paint hook, not added as widgets, so `get_scene`, settle and `changed` read the app exactly as with touches off, and the dots never take a touch. Touches come back on after a hot restart and go away when glint detaches. Debug builds only. The in-app agent is now `ext.flutter.glintAgent7`.
- **The Mac camera on an Android emulator.** `attach device:"<AVD name>" camera:"webcam"` boots the AVD with the Mac's built-in camera as its front camera. It picks the FaceTime camera over a Continuity Camera iPhone, and the back camera stays the emulator's own, since one Mac camera cannot be both. When an emulator camera keeps getting no frames (logcat `Unable to obtain video frame`, which is what a blank preview looks like when macOS has not let the emulator use the camera), `get_scene` warns with the cause and the fix, so a blank preview is not read as an app bug. (#225)
- **Drive the route the app draws.** `location op:route polylineId:"to_dropoff"` reads that polyline's points from the Google map the attached app shows and plays them, so testing "the car follows the route the app fetched" no longer needs the points copied out by hand into a GPX. An unknown id lists the ids the app draws. (#229)
- **Update notice.** Once a day at startup glint asks pub.dev for its latest version, and `attach` says once per session when a newer one is out, so the agent can tell you: `glint 0.4.3 is out (this is 0.4.2): tell the user to run dart pub global activate glint_mcp, then restart the MCP server`. The request sends nothing about you; `GLINT_NO_UPDATE_CHECK=true` turns it off (TELEMETRY.md).

### Fixed

- **On Android, a system dialog over a running app swallowed glint's in-app touches.** A dialog such as "System UI isn't responding" covers the app without changing its lifecycle, so `input:auto` still sent touches into Flutter underneath: the reply said `via app` and the dialog stayed. Before each in-app delivery glint now asks which window has focus; when it is not the app's, the touch goes through the device (`via device (systemSurface)`) and reaches the dialog, and `input:app` refuses with the reason.
- **`scroll_to_find` could not find plain text that was in plain sight.** It counted a target as found only when it would take a tap, so text under an overlay that catches touches never counted: `scroll_to_find text:"took" maxScrolls:6` on Wonderous's Taj Mahal page scrolled for 12.2 s and failed as `scrollLimitReached`. Without `tap:true`, a target painted on screen is now found, with a warning naming what a tap there would hit. With `tap:true` it must still take the tap; when it is on screen but covered, glint gives it one more scroll and then stops with `notHittable`, naming what covers it, instead of spending every remaining scroll.
- **Form fields folded together, hiding validation errors.** Six text fields with different labels shared one fold signature, so `get_scene` showed the first and `… 5 more like it`, and only the first field's error. The fold signature now includes an input's label and error text: differently labelled fields stay separate and an error is never folded away, while list rows with the same label still fold (#234).
- **Typing on Android took seconds.** Android defaulted to `input:device`, so every character went through the on-device server and the keyboard: 28 characters took 3.2 to 3.6 s to deliver on an emulator, and the issue saw 5 to 27 s under load. Android now defaults to `input:auto` like iOS: input goes inside the Flutter app first (the same 28 characters in 10 ms) and through the device for system dialogs, the keyboard and other apps. `input:device` keeps the old behaviour. (#219)
- **A tap that starts a network request reported `nothing changed`.** The response landed after the screen settled, so the change came too late to count. An agent reading `changed: false` would tap again, which on a submit or payment button sends the request twice. When an action looks unchanged, glint now waits up to 1.5 s for the app to rebuild (a response's `setState`, a timer), settles again and re-reads. A late change reports as `contentChanged 900 ms later`, with `lateMs` in the data. A tap that really changes nothing now takes up to 1.5 s longer to say so. The in-app agent is now `ext.flutter.glintAgent6`.
- **`tap text:"Allow"` failed as `internal` when a system dialog was up before the app's first frame.** An app that asks for permission before `runApp` has no widget tree while the dialog waits. When the dialog was already up at `attach`, glint never noticed the app was inactive, so `tap` read the empty Flutter tree instead of the dialog. glint now takes the app's lifecycle at `attach`, so `tap` / `long_press` by text or glintId reach the dialog's buttons. An empty widget tree, from any tool, is now `appNotResumed`: either a system surface is in front or the app has not drawn its first frame yet. When the simulator's accessibility read cannot see the surface, the reply says so and names the way forward. (#233)
- **Buttons from a design-system package had no label and could not be tapped by text.** When a widget's build lives outside the app (a `SangaButton` from a shared package), the inspector shows the widget but nothing inside it, so it read as `unknown kit_button KitButton` and `tap text:"Accept"` found nothing. glint now reads inside such widgets. One that takes taps is a button labelled with the text it paints (`* button kit_button_in_row#6afd Accept`), and one that only paints text is text. (#232)
- **Controls that had faded out were listed as tappable.** Video and call screens hide their controls with `AnimatedOpacity(opacity: 0)` and `IgnorePointer`, but `get_scene` still showed `* button End call`, and the tap was then refused with advice to scroll or dismiss an overlay. A control under opacity 0 now reads `- button kit_button End call [hidden]`, and one under an active `IgnorePointer` / `AbsorbPointer` reads `[ignores touches]`; neither carries a tap or type marker. `tap text:"End call"` on a hidden control says it is faded out and that a tap on the screen usually brings it back, `wait_for text:` does not count hidden controls as shown, and a tap that brings the controls back counts as a change. (#220)
- **A GPX route on the iOS simulator fell far behind and never arrived.** CoreSimulator spends about a fix at every waypoint whatever the speed, so a track with a point every 10 m crawled: at 60 km/h the app moved at about 34 km/h, and when glint said `route finished` it was still 546 m short, with fixes still coming. glint now hands the simulator waypoints at least five fixes of travel apart (about 83 m at 60 km/h), which keeps it within a few seconds of glint's clock. When the route ends, glint pins the device on the last point, so the app is at the destination when glint says it is. (#230)
- **A control faded out with `AnimatedOpacity` or `FadeTransition` still took a tap by glintId.** Flutter hit-tests a widget at opacity 0, and glint's geometry read only the nearest `Opacity` widget, so it called the control painted. `tap glintId:` on it reported `tapped` and, after the wait, `nothing changed`, while nothing showed on screen: on Wonderous's intro, three taps on the hidden next arrow cost about 2 s each. glint now multiplies every opacity the render tree paints above the node (`Opacity`, `AnimatedOpacity`, `FadeTransition` and their sliver forms), so a 0 anywhere up the chain means not painted. `tap` and `long_press` refuse such a node as `notHittable` and say it is faded out (`refuseNotHittable:false` taps it anyway), `awaitReady` waits for it to fade in, and `get_scene`'s `[hidden]` reads the same opacity.

## [0.4.2] - 2026-10-15

### Changed

- An example (`example/example.md`), the package's own analysis options and `dart format` across the package, so it scores fully on pub.dev. The remaining lint notes are fixed; there is no change in behaviour.

### Added

- glint installs from pub.dev: `dart pub global activate glint_mcp`, then point your agent at the `glint` command. Each release tag now publishes to pub.dev after the GitHub Release.

## [0.4.1] - 2026-10-15

### Fixed

- **Typing on a physical iPhone with `input:device`** froze the app when the text had characters the hardware keyboard cannot type (`café ✓`). iOS asks "would like to paste from dtpasteboardd" before an app reads text another process put on the pasteboard, and the prompt blocked the app. glint now taps "Allow Paste" itself (it caused the prompt), and puts the old pasteboard text back only after the app has read the new one. The helper speaks protocol 7.
- **The local network prompt after launch.** `attach launch:` on a phone answered the debug build's local network prompt only while waiting for the VM service, but Flutter can find the service before iOS shows the prompt. glint now also watches for 8 s after the launch.
- **Passcode wording.** `device op:status` said "passcode set" when the phone was locked and needed its passcode; it now says that.
- **A physical iPhone on Wi-Fi only.** Unplugged, a phone stays reachable over Wi-Fi, so screenshots and `device op:status` keep working, but real touches, keys and buttons need the cable. A tap used to fail with `deviceNotConnected` and the advice to put the phone on the same Wi-Fi, which it already was. attach in device mode now warns that the phone is on Wi-Fi only, and a failed touch says the same, with "plug in and unlock" as the next step. Plugging back in recovers without a new attach.
- **Covered-app warning.** attach's warning about an app covered by a system surface now says to tap its button by text, not by x,y.

## [0.4.0] - 2026-10-15

### Added

- `pinch`, a new tool: two fingers around a node (glintId or text) or x,y, spreading (`scale:2`) or closing (`scale:0.5`).
  - It goes through glint's in-app agent with two pointers, or real multi-touch through Device Hub on a physical iPhone with `input:device`.
  - Where the device has no multi-touch (the simulator, Android), it still pinches through the app and says so in `data.input`.
  - `fixtures/media_app` gains a zoom area whose label reads back the zoom.
- `swipe edge:` makes a system gesture from a screen edge on a physical iPhone:
  - `left` (back);
  - `bottom` (home);
  - `bottomHold` (app switcher);
  - `topLeft` (Notification Center);
  - `topRight` (Control Center).

  Top-edge drags register as system gestures from synthetic touches. Bottom-edge ones do not, so home and the switcher use Home presses.
- `type` with text the hardware keyboard has no keys for (accents, emoji, other scripts) works on a phone's device path too. glint puts it on the pasteboard, presses ⌘V, and puts the previous pasteboard text back.

  The Flutter path already typed any text. The helper speaks protocol 6, and the in-app agent is `glintAgent5`.

- A physical iPhone can be acted on, not only read:
  - **`device op:openurl`** opens a URL or deep link on the phone (`devicectl … openURL`).
  - **`kill_app`** stops an app on the phone through `devicectl` (`terminate --kill` on the app's own process, extensions left alone). Before, it ran `simctl` and failed.
  - **`device op:network`**, new, sets an Instruments network condition on the phone: `value:"list"` shows the 22 profiles (100% loss, Edge, 3G, LTE, high-latency DNS, …), a profile id turns it on, `off` clears it. It affects every app on the phone, which the reply says. glint's helper clears it on detach or exit, so it never outlives the session.
  - **`hardware_button`**:
    - `back` is a real swipe in from the left edge;
    - `appSwitcher` is a double Home press;
    - `unlock` wakes the phone and swipes up, and when a passcode is set refuses with `notOnThisDevice`, since only its owner can enter it.

    A swipe from the bottom edge does not register as a system gesture from synthetic touches, which is why the switcher uses Home.
  - **`sensors op:set orientation:`** turns the phone a quarter at a time through Device Hub's rotate, until it reports the orientation, and says so when rotation lock is on or the phone stays put. On the iPhone 15 Pro with iOS 27 the phone did not turn yet, so that is what it currently reports.

  The helper speaks protocol 5.

- More tools work on a physical iPhone:
  - **`record`** records the phone's screen. glint's Device Hub helper writes the display stream to a file on a fresh screen session, so it opens on a keyframe. glint wraps it as an `hvc1` mp4 without re-encoding, so frame extraction and QuickTime both read it.
  - **`device op:status`** reports the phone from `devicectl`: name, model, iOS and build, connection, Developer Mode, whether the developer image is mounted, and whether a passcode is set.
  - **`sensors op:read`** gives the phone's interface orientation, from SpringBoard through the helper. `op:set` answers `notOnThisDevice`, since glint cannot turn a phone yet.
  - **`app_logs native:true`** lists the app's crash reports from the phone (`devicectl` crash logs since attach), as it does on the simulator.

  attach's `not on this device` line drops record, sensors and device status. The helper speaks protocol 4.

- `attach launch:"<project>"` builds and runs on a physical iPhone. It no longer tries to boot the phone as a simulator.
  - **Signing without file edits.** glint passes the team to Xcode through `FLUTTER_XCODE_DEVELOPMENT_TEAM` and picks it in this order:
    1. `signingTeam:`;
    2. the project's own team, if this Mac has its certificate;
    3. the team glint last signed with on this Mac (`~/.glint/signing.json`);
    4. the only team with a certificate;
    5. the team that already has a profile for the app on this phone.

    The reply says which team and why, and names the others. With several teams and nothing to decide between them, or when Xcode cannot sign, the error is `signingFailed` with `data.teams`.
  - **Local network prompt.** While the build launches, glint watches the phone (Device Hub screenshot and OCR) and answers "Allow" on the debug build's "find devices on local networks" prompt. Flutter cannot find the VM service until someone does, and the reply says glint answered it.
  - **One debug session per phone.** A phone runs one Xcode debug session at a time. When another `flutter run` is already debugging it, attach answers at once with `deviceBusy`, naming that process and its project, instead of waiting out the launch timeout.
- Device claims record when their session last acted (at most every 30 s). A claim with no input for 15 minutes reads as idle. attach then drives the device and says so, instead of refusing or warning that input will interleave.

- Faster screenshots on a physical iPhone. glint's Device Hub helper captures the screen through CoreDevice's screen capture service: about 310 ms, against about 2 s for `devicectl`. The first capture of a session takes about 700 ms to connect. It is used for `device op:screenshot`, captures after actions, and reading native surfaces. `devicectl` remains the fallback.
- attach starts the iPhone helper in the background, so the first real touch does not also pay for the connection. `tap sequence` on the phone is one helper command. The helper keeps its screen session for 120 s without input (was 30 s), and speaks protocol 2.

- Actions reply about twice as fast. glint installs a small agent inside the app once per isolate (one eval, the `ext.flutter.glintAgent4` service extension), and three things move into it:
  - **Input.** Taps, swipes, typing and editing keys on the app path each become one call, with nothing to compile per gesture.
  - **Settle.** After an action the agent waits inside the app until:
    - no route or dialog is animating;
    - the scheduler is idle;
    - nothing has rebuilt for 100 ms, or 300 ms have passed, so a blinking caret or a spinner cannot stall it.

    Ink ripples and other paint-only frames are not waited for. Route and sheet transitions are waited out in full, so the reply still reads `routeChanged` or `overlayAppeared` after the animation.
  - **Lifecycle.** The agent posts lifecycle changes, so glint learns a system surface covered the app without polling twice a second. The poll stays only where it also looks for foreign windows (the simulator's XCTest runner).

  On the iPhone 17 simulator with Ember, main → this:
  - tap a field: 1,072 → 764 ms;
  - type 15 characters: 702 → 457 ms;
  - three backspaces: 675 → 397 ms.

  On the media fixture: tap by glintId 587 → 289 ms, by text 612 → 321 ms, raw x,y 540 → 269 ms. A hot restart re-installs the agent on the next call.

### Fixed

- An action that opened a system surface (Control Center, a permission prompt) could report `nothing changed`, because whether the app was covered was read after the action instead of before it. The pre-action snapshot records it now.

- `tap` and `long_press` take `text:` or `glintId:` on a native surface too: a system prompt, an alert, an Android picker, a phone screen read by OCR. glint finds the item on the surface and touches its center, through real touches when the app is covered. An exact label wins over text that only contains it, so `tap text:"Allow"` presses Allow and not the question. A miss is `targetNotFound`, listing what the surface shows.
- Native surfaces come back as data. `get_scene` in native mode, and every action that leaves one over the app, carry `data.surface`:
  - `kind`: permissionPrompt, alert, otherApp or unknown;
  - `title`: the question it asks;
  - `choices`: each button's text and id;
  - the other text on it.

  Replies print it as one line, e.g. `surface: permission prompt · "Allow “Media Fixture” to access your microphone?" · choices: Don’t Allow (native_don_t_allow), Allow (native_allow)`. When the surface could be read, the post-action screenshot is no longer attached.
- What a device cannot do is declared once (`DeviceAbilities`). attach lists it (`not on this device: notifications, sensors, record, …` and `data.abilities`), and tools refuse with `errorKind: notOnThisDevice`, `data.ability` and `data.instead`. On a physical iPhone this replaces:
  - the scattered refusals in notifications, sensors, record and location permission;
  - device status, appearance, openurl, privacy and biometric, which used to fail with a simctl error;
  - `media`, which mistook the phone for an Android device;
  - `shutdown_sim`.

### Changed

- The iOS simulator now defaults to `input:auto`: gestures go inside the Flutter app, with real touches for system surfaces, the keyboard and native views.

  Measured on the iPhone 17 simulator (median of 7):

  | Action | `device` | `auto` |
  |---|---|---|
  | tap by text | 891 ms | 322 ms |
  | tap x,y | 832 ms | 262 ms |
  | swipe | 1,179 ms | 674 ms |
  | long press | 1,380 ms | 876 ms |

  Ember's route push, sheet, typing and back flows give the same change signals either way. `attach input:"device"` keeps the old behaviour. Android stays on `device` until there are numbers for it.
- glint's iPhone helper is 43% smaller (3.07 → 1.75 MB) with no slower screenshots: built with `opt-level = "s"`, one codegen unit, and `panic = "abort"`. `opt-level = "z"` was smaller still but took screenshots about 60% slower, so it was not used.
- One drag builder (`dragPath`) now serves the in-app path, the phone's real touches and its edge gestures, where three copies of the interpolation used to be.

- One input vocabulary on every device. `attach input:` picks where gestures go:
  - `app`: inside the Flutter app;
  - `device`: real touches, which reach system prompts, keyboards and other apps;
  - `auto`: the app first, real touches for what it cannot take.

  It works on the simulator and Android too, where the app path is faster: a tap delivered in 74 ms instead of about 1 s through dtuhid on the iPhone 17 simulator. The defaults stay as they were (`auto` on a physical iPhone, `device` elsewhere). `iosInput` is now only the simulator's real-touch transport, and `iosInput:flutter` still means `input:app`. Re-attaching with another `input` rebuilds the session.
- Every action reply reports how it was delivered in `data.input`, as `{path: app|device, reason?, ms}`, and prints `· via app` or `· via device (systemSurface)`. This replaces the prose `via` string. `reason` is a closed set: systemSurface, keyboard, platformView, outside, noFocus, readOnly, unsupportedKey.
- attach's tested-setup block moved from `data.input` to `data.setup`, and its line reads `input: auto · setup: iOS 27.0, … · verified`. The route is in `data.inputRoute`.
- Failures an agent handles differently have their own `errorKind`:
  - `deviceNotConnected`: the phone is unplugged, locked before trust, or out of Developer Mode;
  - `developerImageMissing`;
  - `deviceBusy`: another screen viewer holds the phone;
  - `inputPartial`: `data.delivered` of `data.of` landed, and nothing was retried.

  Before, all of these were `unsupportedBackendAction` with the reason in prose. The device-mode paths of `type`, `key`, `hardware_button` and raw x,y gestures keep these kinds and their next steps.

## [0.3.0] - 2026-10-15

### Added

- glint drives a physical iPhone. Before, every gesture was refused with a point to ask the user to tap. Input now takes one of two paths, and each action reply says which in `via`:
  - Inside the Flutter app (the default): pointer events go straight into the app's gesture system and text edits into the focused field, through the VM service. A tap lands in about 10 ms, at the exact logical point, and formatters see each typed character. Nothing needs installing, signing or approving.
  - Real touches through Device Hub, the service Xcode 27 uses to control a device: taps, drags, the hardware keyboard, and the home, lock and volume buttons, over the CoreDevice tunnel the Mac already has. glint runs a small helper for this, `glint-devicehid` (`native/ios_device_hid`, built on a pinned [`idevice`](https://github.com/jkcoxson/idevice), shipped as a release asset). It needs Developer Mode and nothing on the phone itself.
  - `iosInput:auto` (the default) uses the Flutter path and moves a gesture to Device Hub when Flutter cannot take it: a system alert or permission prompt is over the app, the point is on the keyboard or a native view, no Flutter field has focus, or the key has no text-editing equivalent. `iosInput:dtuhid` sends real touches only. `iosInput:flutter` stays inside the app and says why when it cannot.
  - A Flutter edit that fails partway is reported with how much landed, and is never retried through Device Hub, so nothing is typed twice.
  - `attach mode:device` works on a paired iPhone with no Flutter app, sized from a `devicectl` screenshot and driven through Device Hub.
  - When something native covers the app (a system prompt, Control Center), `get_scene` reads it: the text on a `devicectl` screenshot, found with macOS Vision, listed with tap points. Action replies report `nativeSurface` and `nativeDismissed` as they do on the simulator.
  - `attach iosInput:` with a different value on an attached iPhone rebuilds its input instead of switching back to the old one.
  - Raw `x,y` taps, long presses and swipes report `via` too, and a refusal keeps its reason and next steps.
  - Device Hub stops its screen session after 30 s without input, and leaves alone a session another viewer started.
- `notifications` on the iOS simulator presses a notification's buttons, and opens entries that are only in the Notification Center. `op:action` pulls the banner down, finds the button on a screenshot with macOS Vision text recognition, and taps it: the menu is outside SpringBoard's accessibility tree, and text that was on screen before the pull-down is ignored. glint builds the OCR helper from `native/ios_ocr/ocr.swift` with the Xcode toolchain on first use and caches it. The simulator does not open a Notification Center entry from any injected tap. For a push glint sent itself, `op:tap` and `op:action` clear that entry, send the same push again, and act on its banner, saying so in the reply. The XCTest runner speaks protocol 4 (a new `/tapElement` route) and rebuilds once.
- `media op:mic` feeds audio into the microphone of every app that records on an Android device: a tone (`hz`), speech (`text`, macOS `say`) or a host audio file, looped for `durationSec`. `stop:true` says which apps recorded it and for about how long. glint's device server (shell) registers a loop-back audio policy, the way Android's own tests inject microphone audio, so it needs no host microphone permission and no emulator control. It should work on phones too; that is not verified yet. The emulator's gRPC `injectAudio` was dropped: on macOS it crashes emulator 36.6.11 and 37.2.12 when audio arrives with no recorder open, and on 36.6.11 the audio never reached apps. The device server speaks protocol 2 (#137).
- `sensors`, a new tool for how the device is held (#162):
  - `op:read` gives the device orientation (portrait, portraitUpsideDown, landscapeLeft, landscapeRight, faceUp, faceDown), the interface orientation and whether rotation is locked. On Android it also gives the newest accelerometer, gyroscope and magnetic field samples, from `dumpsys sensorservice` on a phone and from the emulator console on an emulator. The orientation is worked out from gravity, so "is the phone flat or is the stream rotated" has an answer.
  - `op:set orientation:` drives it. The Android emulator gets it through its accelerometer, so the system's auto-rotate and the app's motion sensors both see it, and arbitrary `acceleration:[x,y,z]` works there too. The iOS simulator gets it through the XCTest runner (`XCUIDevice.orientation`), face up and down included. The reply reads the state back and warns when the screen in front did not rotate or rotation is locked.
  - `op:script steps:[…]` runs a motion sequence of orientations, accelerations, waits and (Android emulator) shakes, with progress every 15 s. A step this device cannot take is refused before anything runs.
  - Physical Android phones are read only. A physical iPhone is not supported.
  - The XCTest runner speaks protocol 3 (a new `/orientation` route) and rebuilds once on first use.
- `notifications`, a new tool for the system notifications of the attached app (#168):

  - `op:answer choice:allow|deny` answers the system prompt asking to allow notifications.
  - Pick one with `text` (title or body) or `index`.
  - On Android, the list comes from `dumpsys notification`. tap, action and clear open the real shade, read it through glint's device server (or `uiautomator dump` when the server is not running), expand a row whose buttons are folded away, and touch it as a person does.
  - On the iOS simulator, glint starts its XCTest runner (built on first use, with progress every 15 s). It reads banners and the Notification Center from SpringBoard, pushing a showing banner into the Notification Center and expanding the app's stack first. It taps a banner while it shows, and clears by swiping each entry away.
  - Not possible on the simulator yet, and reported as `unsupportedBackendAction` with the reason: pressing a notification's buttons (SpringBoard hosts that menu outside the accessibility tree), and opening an entry that is only in the Notification Center (injected input leaves the app suspended while the cover sheet is up). Android has no simulated push, so `send` is iOS only.
  - `fixtures/flows_app`'s chat posts Amara's reply as a notification with Reply and Mark as read when the app is in the background.
- `device op:screenshot` shapes the image for a quick look (#167):
  - `glintId:` crops to that widget with 8 points of margin. `region:{top, bottom, left, right}` crops to fractions of the screen. A crop comes back inline, at most 720 pixels on its longest side, with a `coordinates` line that maps image pixels back to logical points for a tap.
  - `apps:[…]` captures several attached apps and returns one image with them side by side, each scaled to the same height, plus a left-to-right legend naming each app and device. It combines with `glintId` and `region`.
  - `afterMs` waits before capturing, and `waitFor:"<text>"` first waits (up to 15 s) until the app, or the first of `apps`, shows that text.
  - Screenshots of an attached Android app now work. `device op:screenshot` used to refuse Android outright.
- Multi-device scenarios in one call (#165):
  - A `batch` step may name its own `app:`, so one batch drives several attached devices. Before, a step's `app:` was dropped without a word and the step ran on the active app, so a tap meant for the second phone landed on the first. An `app:` that matches no attached app (or several) stops the batch with `unknownApp`. Each step line names its app (`3. [emulator-5556] wait_for …`).
  - `wait_for`, a new tool: wait until an app shows a text (matched as `tap text:` matches, app bar titles included) or a `glintId`, or with `gone:true` until it disappears. With `app:` it watches another attached app, so in a batch one device waits for what another caused. `timeoutMs` defaults to 15 s (max 120 s). It reports progress every 15 s and, on a timeout, fails with `targetNeverReady` and the text the app shows instead. It also runs as a `batch` step, and batch passes its progress token to its steps.
  - `tap text:` and the other text targets also match app bar titles.
- Fewer wasted calls when targeting (#169):
  - `tap`, `long_press` and `resolve` take `text:` instead of `glintId`: the visible text of a button, tile or label, matched exactly first (ignoring case), then as a substring. An open dialog is searched before the screen, so a dialog button with a generic id (`gesture_detector_in_overflow_bar#xm3q`) is one call: `tap text:"Try again"`. The tap lands on the nearest tappable ancestor of the text. Several matches fail with each candidate's id and text; no match fails with the text on screen. With `awaitReady` the text is waited for.
  - `glintId` is accepted on every tool whose target has its own name: `type` (`focus`) and `scroll_to_find` (`targetGlintId`).
  - `key key:back` presses the system back, the same as `hardware_button button:back`. Other device buttons passed to `key` point at `hardware_button`.
  - `scroll_to_find tap:true` taps the target once it is on screen (its nearest tappable ancestor for a text match) and returns the tap's result, so finding and tapping an item below the fold is one call.
- `device op:privacy` works on Android (pass the adb serial as `udid`; `bundleId` defaults to the attached app). Services keep the iOS names where they exist: notifications, microphone, camera, contacts, location, location-always, photos, media-library, calendar, motion, plus phone, sms and all. `grant`, `revoke` (marked as the user's answer) and `reset` (the app asks again) go through `pm`, after checking the app declares the permission, and are read back. `screen-capture` sets the MediaProjection app op (`appops set <package> PROJECT_MEDIA allow|ignore|default`). Before, every Android call failed with simctl's "Invalid device"; the other `device` ops now say they are iOS-only (#166).
- `map`, a new tool that drives a Google map like a finger (#148, phase 5):
  - `op:read` gives the camera and the markers with their screen points.
  - `op:tap marker:` taps a marker where it is drawn.
  - `op:pan` moves the map by `dx`/`dy` points, or centers `to:"lat,lng"` or a `marker`. It re-reads the camera after each slow drag until the target is within 25 points, sends progress every 15 s, and stops with `unsupportedBackendAction` when the map does not move under drags.
  - `op:zoom direction:in` double-taps the map. `out` tries the one-finger double-tap-and-drag and says plainly when the map did not zoom, since glint has no second finger.
  - Every reply gives the camera before and after.
  - Checked on the iOS simulator. The fixture's Android map has no Maps API key, so Android draws a blank map that takes no gestures, and Android is not verified.
- Location replies say whether the attached app is in the foreground (`appInForeground`) and whether it can get location in the background at all (`backgroundLocation`: the `location` background mode in the iOS app's Info.plist, or ACCESS_BACKGROUND_LOCATION declared on Android). They warn when a backgrounded app gets no fixes and say why. An iOS app that does not answer in the background is reported as suspended rather than failing the call. `fixtures/ride_app` markers report taps ("Tapped Pickup").
- `location op:wait` blocks until a route arrives (`until:"arrived"`), reaches `progress` or a `waypoint`, or the position is `near` a point (`at`, `withinM`), and optionally until the attached app also shows `text` (for example "Driver arrived" in a rider app while a driver route plays on another device). It sends progress every 15 s with the route's progress and distance left, and fails with `targetNeverReady` on a timeout or a route that stopped, saying which part was met. `fixtures/ride_app` gains Rider and Driver modes that share the driver's position through a small host relay (`relay/relay.dart`), so a two-device ride can be tested end to end. The README has the two-device recipe (#148, phase 4).
- `get_scene` reads Google maps (#148, phase 3). A `GoogleMap` is now a `map` node with its live camera (`camera 6.52440, 3.37920 zoom 15.0 · shows 6.51184..6.53696, 3.37083..3.38757`), and its markers, routes (polylines) and areas (polygons and circles) are listed under it. Each marker shows the screen point to tap, in logical points (`marker pickup "Pickup" at 6.52440, 3.37920 @ 195,398`), or `(off screen)`. Markers, routes and areas come from the widget; the camera and the screen points come from the map's controller, read asynchronously over two evaluations (about 0.3 s on the iOS simulator, 0.5 s on the Android emulator, and only when a map is on screen). Map lines are exempt from the 40-character label cap, since every digit counts. `fixtures/ride_app` draws a trip: pickup and drop-off markers, the route and a pickup zone.
- `location` permissions and the system prompt (#148, phase 2). `op:permission value:` sets the app's location access without a prompt: `whileUsing`, `always`, `approximate` (Android), `deny` or `reset` (the app asks again). It goes through `simctl privacy` on the iOS simulator and `pm grant`/`revoke` with permission flags on the Android emulator, checks the app declares the permission (background location for `always`), and reads the result back. `op:answer choice:` taps the open system location prompt (`whileUsing`, `once`, `deny`, `always`, `keepWhileUsing`), with `precise:false` choosing Approximate on Android first; on iOS it needs the XCUITest runner. `op:services value:on|off` switches location services on an Android emulator. Every location reply now carries the app's permission (`notAsked`, `denied`, `once`, `whileUsing`, `always`, `approximate`), read from the simulator's locationd records or `dumpsys package`, and warns when the app is denied or has not been asked, so a fix it never sees does not pass silently. `fixtures/ride_app` shows its permission and accuracy, catches location errors, and has a Try again button that asks again.
- `location`, a new tool for simulated GPS on the iOS simulator, the Android emulator and a paired iPhone. `op:set at:"lat,lng"` sets one position; `op:route` travels points, a GPX or KML file, or an encoded polyline in the background at `speedKmh` or over `durationSec`, while the agent keeps using the app, with `loop`, `jitterM` (GPS noise) and `dropout` (lost fixes); `pause`, `resume`, `stop` and `seek` (progress, meters or waypoint) control it, and `op:get` reports progress, distance and time left. On the iOS simulator glint hands each leg to the simulator, so the app gets a real heading (with noise or dropouts it sends one fix at a time instead); the Android emulator takes each fix through its gRPC `setGps` with speed and heading; an iPhone goes through `devicectl` at most every 2 s. On Android, replies also say whether location is on and whether the app holds a live location request, so a fix the app never sees does not pass silently. `op:clear` stops simulating; an emulator keeps its last fix and says so. Physical Android phones are refused with the reason. A new fixture, `fixtures/ride_app`, shows the position on a Google map (#148).
- `attach device:"<AVD name>"` boots an Android virtual device from glint's own process when nothing runs it (on a free console port, with progress every 15 s), then attaches in device mode, or starts the app when `launch:` is given. glint asks the emulator for its gRPC control, which it does not always start by itself, so the camera feed and `listen` work on it. When that AVD already runs, the name maps to its serial instead of starting a second copy, which the emulator refuses. `attach dryRun:true` lists the AVDs that are not running (#151).
- `media op:camera` sets what an Android emulator's cameras see, live: an image, a video or the glint test card. Run `setup:true` once, which puts the AVD's cameras in the emulator's `environment` mode (one emulator restart; `setup:false` undoes it). Each source then goes in through the emulator's `setEnvironment` gRPC call and shows at once, even in a camera preview that is already open. glint fits the source into the part of the camera frame an app actually sees, so the whole picture lands in view, and a photo the app takes of the test card decodes with `media op:inspect`. No macOS camera extension, approval or extra app is needed. The iOS simulator has no camera, and phones film what is in front of them, so both say so (#137).
- `media op:event` sends device events to an Android emulator, and each one reads the device back before saying it worked: `rotate` (portrait, landscape, the reverse ones, or `auto` to hand rotation back to the sensor), `light` (lux), `proximity` (near or far), an incoming `call` and `endCall`, and an `sms` (it waits for the message to reach the inbox, so OTP flows can be tested). They go through the emulator console via `adb emu`, or settings for rotation. The iOS simulator and phones say they cannot (#137).
- `media op:listen` records what an Android emulator plays, through the emulator's own gRPC control endpoint (found from its running-instance file, no setup). Start it, make the app play, then `stop:true` returns a WAV with how long there was sound, peak and average level in dBFS, and the silent stretches, so an agent can check that a voice note, ringtone or exported clip actually makes sound. The iOS simulator and phones say they cannot. A new fixture, `fixtures/media_app`, records the microphone and plays a beep or the recording. Feeding the emulator microphone was dropped for now: the emulator's `injectAudio` crashes emulator 36.6.11 on macOS (#137).
- `media op:permission` sets camera, microphone or photos access for the app: `grant`, `deny`, `reset` (the app asks again) or `limited` (photos, Android 14 and later). Android goes through `pm grant` and `pm revoke`. glint first checks that the app declares the permission, because Android 15 accepts a grant for an undeclared permission silently, and then reads the result back. The iOS simulator goes through `simctl privacy`; it has no camera setting and no limited photos, so those say to answer the app's own prompt instead. `device op:privacy` no longer suggests a `camera` service, which simctl does not have (#137).
- `media op:pick` chooses a photo or video in the open system photo picker: `name:` a seeded asset, matched by its seed time in the picker's labels (to the second on Android, to the minute on iOS, with newest-first order breaking ties), or `index:` (0 = newest). It taps the cell, taps Add or Done when the picker asks, and says whether the picker closed. Seeded files now carry the seed time, so the gallery dates match. On iOS it needs the XCUITest runner (`attach iosBackend:"xctest"`), the only way glint can read the picker; without it, it says so (#137).
- Physical iPhones. `attach` finds a paired iPhone that is connected now (through `devicectl`) and matches an app to it by its `flutter run -d <udid>`; before, a phone's id was never recognised and attach only offered simulators. `get_scene`, `hot_reload`, logs and the network tools work through the VM service as on a simulator, and screenshots come from `devicectl`. glint cannot send input to a phone yet, so `tap`, `type`, `swipe` and the rest return `unsupportedBackendAction` with the point to ask the user to tap, in logical points (#136).
- `media`, one tool for the media loop of an app, on iOS simulators and Android emulators in Flutter or device mode. `op:"seed"` puts a photo or video in the gallery (Photos through `simctl addmedia`; MediaStore through `adb push` plus the `scan_file` provider call, which also takes audio) from a host file or a built-in generator, and returns the asset name, size and device path. On Android, `clear:true` removes only what glint seeded, tracked in `~/.glint/media`; the iOS simulator has no supported way to delete from Photos, so there it says which `glint-` items to delete in the Photos app. The `testcard` generator renders a self-describing clip or photo with ffmpeg: four colored corner patches, a frame number and timecode, binary strips that encode the frame index, frame count and original size, a white flash and a 1 kHz beep at every whole second, and an optional rotation tag. `speech` (macOS `say`) and `tone` make audio. `op:"files"` lists what the app wrote in its sandbox, newest first, with `since:"lastAction"` or an ISO time and a `glob`, and `pull:true` copies one file to the host. `op:"inspect"` reads a host file or a pulled device file: ffprobe metadata, loudness, and frames returned as images; a glint test card also decodes to a verdict such as `testcard: rotated 90, not mirrored, downscaled 1080x1920 to 360x640, 168 of 180 frames (12 dropped), audio 100 ms late`. A missing ffmpeg, ffprobe or `say` is reported as `unsupportedToolchain` with the install step, and slow work sends progress every 15 s (#137).
- `attach launch:` also takes an installed app id (an iOS bundle id or an Android package) and reopens that debug build in seconds without a rebuild. glint reads the app's VM service address from the simulator log or logcat, then pairs it with `flutter attach` in the project folder it remembers, so evaluation and `hot_reload` work as after a `flutter run`. It refuses an app that is already open, one glint has no project folder for, and a physical iPhone, and each failure names the next call. When an app is gone from a device, the next steps list the reopen first and the rebuild second (#103).
- `hot_reload` reloads or (with `restart:true`) restarts the attached app through the services its own `flutter run` registered, so code changes can be applied without a shell and only the app under test is touched (#118).
- Apps and devices are owned by the session that attached or launched them. `kill_app appId:` refuses an app this session never attached, and `shutdown_sim` refuses a device it never attached or launched on (including any in `all:true`), with the new `errorKind: notOwned`; `force:true` overrides. `attach` and the session's app list show the app's project root (#118).

- Android input through glint's own resident server: a small `app_process` server holding one UiAutomation connection, reached over an adb-forwarded socket. Taps, swipes, long presses and keys go through it, text of any script types (key events, or the field's text for characters no key makes, so `zoë` works where `adb shell input` fails), and native surfaces are read from every window instead of a `uiautomator dump`. `adb shell input` stays the fallback, with a warning saying why (another tool holding the accessibility connection is named). `attach androidInput:auto|server|adb` overrides; the attach `input:` line names the path. Releases attach `glint-android-server.dex` with a sha256, downloaded on first use like the iOS bridge.
- A second iOS backend: glint's own XCUITest runner (`attach iosBackend:xctest`). It is built once per Xcode into `~/.glint/xctest` (about 70 s the first time, rebuilt when glint ships a changed runner), runs as a long test that serves glint on a local port, and is reused across sessions. Taps, swipes, long presses, Unicode text, keys and home go through XCTest; screenshots, recording, lock and unlock stay on the bridge. Build and start failures name the step and the compiler or log line.
- Device claims (#102). Each glint session claims the devices it attaches to (`~/.glint/claims`). `attach` will not auto-pick a device another live session is driving, and refuses with the new `errorKind: deviceClaimed`, naming the holder. Passing `device:` still attaches, with a warning that input will interleave. `attach dryRun:true` marks claimed devices. Claims of sessions that have exited are ignored.

### Changed

- `attach device:` could answer "2 running apps on <device> — pick one by app" for a simulator running one Flutter app (#135). One app shows up under two VM service URIs (its DDS and the raw VM), and glint merges them by bundle id. It looked the bundle id up from the apps running on the simulator, and with any second app there (glint's own XCTest runner host after `iosBackend:"xctest"`, or the `notifications` and `sensors` tools) it gave up. One URI then had no name and stayed a second entry. The lookup now counts only Flutter apps, so the helper app no longer makes the device ambiguous.
- The back, close and drawer buttons an app bar adds by itself were missing from the scene, because Flutter builds them inside `AppBar`, `SliverAppBar` and `CupertinoNavigationBar` rather than in the app's code. They now show as `* button back_button Back` (`cupertino_navigation_bar_back_button`, `close_button Close`, `drawer_button Open navigation menu`), copied from the full widget tree into each visible app bar, and are no longer marked `[disabled]` for their empty `onPressed`. On the iOS simulator, `hardware_button back` taps that button when the edge swipe changes nothing twice: pages under a go_router `StatefulShellRoute` refuse the swipe, so on `fixtures/flows_app` back never left a screen before.
- Apps on go_router (and other `Router`-based navigation) always read `route: /`, and moving between screens reported `contentChanged` instead of `routeChanged`. glint now reads the router's own location (`/send`, `/send/amount`, `/checkout` in `fixtures/flows_app`) through the router's `restoreRouteInformation`, which every `Router` implements. A screen pushed with `Navigator.push` on top of a router page reads as `/checkout > MaterialPageRoute`. The innermost visible page is probed first, falling back to the outer one, so the location of the screen in front is read rather than the shell's.
- A `#hash` id could change when something near it changed, so an id read from one reply failed in the next call. On send money's PIN screen in `fixtures/flows_app`, the whole keypad got new ids once `Wrong PIN, try again` appeared above it, and on the ride screen `Raise fare` got a new id every time the fare it raised changed. An id's hash now follows each widget's type and its position among siblings of the same type, so a new text above a keypad leaves the keys alone, and an item that is the only one of its type in a list is keyed by that type rather than by its text. Ids with a `#hash` change once with this release.
- A tap that only changed how something looks reported `nothing changed`, for example the PIN dots that fill in as each digit is typed on send money's approve screen in `fixtures/flows_app`. Actions now also compare what the screen paints (fills and borders, opacity, elevation and colour of material surfaces), read in one evaluation before and after, so a colour-only change reports `contentChanged`.
- Buttons now say what they would do. A `ListTile` with a tap handler is tappable; before, it read as a static container, since its `InkWell` is built by Flutter. A button with no handler (`onPressed: null`, a gesture detector with nothing to do) reads `[disabled]` and loses its tap marker. An icon-only button takes its tooltip as its label (`Lower fare`, `Close`).
- `TabBar` tabs are named and their current one is `[selected]`, like the navigation bars (their text is a string, so the scene never saw it), including a tab bar in an app bar's `bottom`.
- State-management builders (`Obx`, `BlocBuilder`, `Consumer`, `ValueListenableBuilder`, `StreamBuilder` and the like) no longer show as empty `unknown` lines, and a button that only wraps another button (a dialog's TextButton > InkWell > GestureDetector) reads as one.
- Screens built on `CupertinoPageScaffold` (or `CupertinoTabScaffold`) were taken for dialogs: glint recognised a page only by a Material `Scaffold`, so opening a Cupertino screen reported `overlayAppeared` and its content was mixed into the screen under it. Cupertino page scaffolds now count as pages everywhere glint looks for one.
- Pages covered by another route stayed in the scene inside shell routes and nested navigators, so a pushed screen was listed together with every screen under it (and ids shifted with what else was listed). glint now treats a page whose route is built with its tickers off (`TickerMode.of`, which Flutter's overlay does for covered routes) as hidden.
- A local iOS bridge build always won over the downloaded bridge, even when it was older than glint expected. An old checkout's build of `native/ios_sim_bridge` was used silently, missing later fixes, such as Xcode 27's move of SimulatorKit to `Contents/SharedFrameworks` ("SimDeviceLegacyHIDClient not found"). glint now passes over a local build that predates the version handshake, speaks another protocol, or is older than the bridge sources beside it, uses the downloaded bridge instead, and says so. The bridge also loads SimulatorKit from `SharedFrameworks` up front, and finds Xcode through `DEVELOPER_DIR` or `xcode-select` in both of its loaders (one assumed `/Applications/Xcode.app`) (#161).
- After a hot restart, glint could bind to the wrong isolate and stay there until a full relaunch. Apps with push or background-task plugins run a second, headless Flutter engine whose isolate registers the same Flutter extensions but has no widget tree. When the restarted UI isolate took a moment to start, glint picked the headless one: scenes then failed with `getRootWidgetTree … result: null`, or the app read as backgrounded (`lifecycle: detached`) and a native surface. glint now prefers the isolate whose widget tree is ready (`ext.flutter.inspector.isWidgetTreeReady`), waits up to 15 s for it after a restart, and moves to a new isolate when the current one has no tree (#170, #121).
- Hidden tabs were read as if on screen on Flutter 3.47 and later: `IndexedStack` stopped wrapping hidden children in a `Visibility` widget, which is what glint looked for, so every tab of an `IndexedStack` or stateful shell route was listed. glint now asks `Visibility.of`, which works on old and new Flutter, and lists only the visible tab.
- Navigation bars (`NavigationBar`, `BottomNavigationBar`, `NavigationRail`, `CupertinoTabBar`) showed as bare, untappable icons, since their labels are plain strings rather than widgets. They are now a `tabs` container of tappable buttons named by their labels, with the current one `[selected]`.
- A sheet or dialog opened from a page inside a nested navigator (a shell route, a tab with its own stack) was missed: glint read only the root navigator's overlay, so the sheet's content showed inline in the page, no `--- dialog ---` section appeared, the action that opened it reported `contentChanged`, and buttons under it still read as tappable. glint now reads nested navigators' overlays too. The sheet shows under its own section, the screen under it reads as blocked, the opening tap reports `overlayAppeared`, and a tap on a covered button is refused with `notHittable` (#171).
- `get_scene` cut every label at 40 characters, so a sentence lost its end ("… heading 1…"), even when drilling into that one node. On-screen text now keeps up to 80 characters in a full scene, other labels stay at 40, and `get_scene glintId:` shows the node's text whole.
- On Android, every attach warned that the glint Android server could not be downloaded, and input fell back to `adb shell input`: the 0.2.0 release predates the server, so it has no prebuilt `glint-android-server.dex`. When the download fails, glint now builds the server from its own sources (javac against the newest `android.jar`, then `d8`, as `native/android_server/build.sh` does) and caches it in `~/.glint/bin`. The warning remains only when no Android SDK or JDK is there to build with.
- `attach` counted a remembered app whose project folder had since been deleted as launchable, then failed with "could not start `flutter run`: No such file or directory". glint no longer starts or offers such records, and `attach dryRun:true` marks them "project folder gone".
- Segmented controls (`SegmentedButton`, the Cupertino segmented controls) were invisible: Flutter builds each segment's button inside the framework, so only an unknown node reached the scene, and an app bar dropped it. Each segment's label is now a tappable button, and a selected segment reads `[selected]`.
- A route on the Android emulator could stop moving partway while still reporting progress: one `setGps` call that never returned left the route waiting on it forever, so later fixes were skipped and the device kept the old position. Each emulator call now has a 5 s deadline, every fix a 20 s one, and the end of a route is always sent.
- Markers, routes and areas under a map no longer fold into "… N more like it"; each is its own line.
- `media op:camera` found an emulator's AVD only through the running record the emulator writes when it starts gRPC. An emulator launched from a sandboxed shell writes none, so camera setup failed with "could not find the AVD". glint now asks the emulator console (`avd discoverypath`, then `avd name` and `avd path`) when no record matches, so setup and undo work. The camera feed and `listen` need gRPC, which such an emulator does not have; they now say so and name the fix (close it, then `attach device:"<AVD name>"`) instead of a generic "found no control endpoint" (#151).
- `attach` on an app that is already attached, with a different `iosBackend` or `androidInput` than its session uses, switched to the old session and silently dropped the backend, so the `media op:pick` next step (`attach iosBackend:"xctest"`) could never work. It now rebuilds the session on the asked-for backend and says `re-attached Ember on xctest (was bridge)`; when the Android server cannot start it says input still uses adb, with the reason. The same backend still switches instantly (#150).
- `long_press` holds for 800 ms by default instead of 500 ms. 500 ms equals Flutter's long-press threshold, so about half of default long presses ended just before Flutter recognised them (#112).
- An unplugged physical Android phone was reported as a closed emulator, with a next step to boot it. It is now reported as disconnected, with "ask the user to reconnect the phone, then attach" (#120).
- A tap on a native surface (a system alert, permission dialog or another app) reported `changeCategory: nativeSurface`, which reads as success, even when the surface did not react. glint now compares the screen before and after (giving native animations time to finish): unchanged means `changed:false`, `changeCategory: nothing` and a warning to check the coordinates or ask the user to tap; changed means `changed:true` (#115, #119).
- Native crashes next to Dart logs. `app_logs native:true` lists the app's native crashes since attach: the simulator's crash reports on iOS (exception, signal and the crashing thread's top frames), and Java exceptions and native tombstones from the crash log buffer on Android. When the VM drops because the app crashed, the `connectionLost` reply now says "the app crashed" with the reason and frames instead of guessing at a hot restart. A lost connection that reached a tool wrapped in another error (`Service has disappeared`, `Service connection disposed`) is now reported as `connectionLost` too, instead of `<tool> failed` with `errorKind: internal`.
- Tool definitions are 12% shorter (32.6k to 28.5k characters, about 1,000 fewer tokens on every turn). The `app` argument and the gesture arguments shared by tap, long_press, swipe, drag, scroll and type now use one tight wording each, and the ten longest tool descriptions no longer repeat what their arguments and the instructions already say. No argument or behaviour changed.

### Fixed

- `media op:inspect` missed a glint test card that sat inside black bars, as it does in a camera photo; it now finds the picture with ffmpeg's `cropdetect` and decodes it there. A JPEG was read as a 0.04 s video, so `frames` returned nothing for it; still images now count as photos.
- On Android, attaching while a native surface (the photo picker) covered the app left glint unable to tell the surface from the app, because it learned the app's package only while the app was in front. It now starts from the package attach already knows. The project folder attach reports was the Flutter SDK for apps under `flutter run` on Android (any folder with a `pubspec.yaml` passed); it now has to be a Flutter app, found from the DDS or its `flutter run` parent.
- `attach device:` on a device another live glint session had claimed took the claim away: the warning said the inputs would interleave, but the claim file then named the new session. When that session exited, the device looked free to every other agent while the first session was still driving it. The first session now keeps its claim (#139).
- When `attach device:X` could not settle on one app, the reply listed every running app and every booted device as next steps, so apps on other devices read as if they were on X. Now only apps on X are offered. Apps elsewhere get one line marked "not on X, so only if you mean another device", and the device list is left out because a device was already chosen (#135).
- `type` could report success while the field held the wrong text. On a busy simulator a held key repeats, and iOS turns a repeated space into ". " (`hello glint` became `hello. glint`), but the check compared letters and digits only, so it passed. For a field with no formatters of its own, glint now requires the field to hold exactly its old text with the typed text inserted. When a field that started empty does not, glint clears it and retypes once at 40 ms a key, then says what happened: fixed by the retype, rewritten the same way twice (the app's own formatting), or still wrong. Only lengths are reported, so no password leaves the app. This is what kept failing the nightly iOS device check (#75).
- Native UI an iOS app presents inside its own process (the system photo picker, the text edit menu) was invisible: the app stays `resumed`, so a tap that opened the picker reported `overlayDismissed` and a long press that opened the edit menu reported `nothing changed`. With glint's XCUITest runner attached (`attach iosBackend:xctest`), glint reads the app's accessibility tree after each action and in `get_scene`. The action reply says `nativeSurface` and names it (`native screen "Photos"`, `menu (Paste · Select All · Scan Text)`, or a system alert), and `get_scene` lists its elements with tap coordinates instead of attaching a screenshot. Closing it reports `nativeDismissed` (#80).
- `type clear:true` deleted only the text before the cursor, which a tap leaves mid-field, so text after it survived and the new text landed in the middle (`wisdomiyamu.ember@gmail.commbe…`). Clearing now also forward-deletes what is left.
- On Android, the first keys typed into a field just switched to were lost while the keyboard reconnected (a 9-character password arrived as 5). `type focus:` now gives the keyboard 300 ms to take the new field before typing.
- `type` reported `contentChanged` even when most keys never reached the field. It now reads the field back and warns, with lengths only, when the typed text is not there (letters and digits compared, so input formatters do not count).
- A glintId stopped resolving when its `_in_<parent>` part or `#hash` changed between reads, which happens when another node with the same name appears or leaves (a text field read as `text_field_in_qc_glass_card` before focus and `text_field` after). An id that no longer exists now resolves to the one node of the same name built at the same source location as the id's earlier holder, so `focus:` and taps taken from an earlier scene keep working. A stale id never resolves to a different widget (#117).
- A bottom sheet or dialog that contains a text field was left out of `get_scene` (only the page below showed, with no overlay marker), because any overlay holding a `TextField` was taken for the cursor handles and copy/paste toolbar. Only an overlay with no editable field counts as that chrome now. Fields inside sheets and dialogs also get their label, value and error read, so typing into them reports a change (#111).
- iOS (Indigo input): every key and touch event waited up to 2 s for the simulator's acknowledgement before the next was sent, so on a loaded machine a key stayed pressed for seconds and repeated (`hello glint` typed as `hello. glint`), and typing 11 characters took up to 80 s. Presses now go out at once and each release waits for everything still unacknowledged, so a key or finger is held only as long as intended (#75).
- iOS taps are a short held contact (down, a move frame at the same point, up after about 100 ms) instead of a bare 50 ms down/up, the same shape as the zero-length swipe and 120 ms long press that landed reliably where plain taps were dropped (#113).
- `attach launch:` accepted any folder with a `pubspec.yaml`, the Flutter SDK included, and then waited out the whole launch timeout (180 s) before failing. It now refuses at once unless the folder is a Flutter app (a `flutter` SDK dependency and `lib/main.dart`), names what is missing, and lists apps glint launched before. A named Android device (`emulator-…` or one discovery lists) is launched as Android instead of going through `simctl boot` (#103).
- When the app on the `device` you named is gone and another device has one, attach no longer suggests omitting `device` (which moves you onto the other device). It leads with relaunching on your device when glint launched an app there before (#103).
- A photo set as a `BoxDecoration(image: DecorationImage(...))` on a `Container`, `DecoratedBox` or `Ink` was missing from `get_scene`, because those wrappers are dissolved before anything reads them. They are now checked for a decoration image in the same eval as the other images (at most 12 per scene). A childless one shows as `- image <id> banner.jpg`, and one with children shows `- image <id> banner.jpg (background)` ahead of them. Wrappers without an image dissolve as before, and swapping the photo counts as a change (#79).

## [0.2.0] - 2026-09-27

### Added

- iOS input over `dtuhidd` on Xcode 27. Once anything starts dtuhidd on a simulator boot, the simulator drops taps, keys and buttons sent the old way (Indigo) until it reboots; that was #74. The bridge now sends touch, keys, home and lock through dtuhidd when CoreSimulator ships it, falls back to Indigo when it does not answer, and says which it used. `attach iosInput:indigo|dtuhid` overrides the choice, and the attach `input:` line and the tested setups name the transport. Bridge protocol 2.
- Xcode 27 support. Xcode 27 moved SimulatorKit to `Contents/SharedFrameworks`; the bridge now loads it from there, and every bridge action (tap, tap sequences, long press, swipe, typing, keys, lock, unlock, home, back, recording) is verified on Xcode 27.0.
- iOS `attach` checks the toolchain and reports it under `toolchain`: the Xcode version, where the bridge came from, and its protocol number.
- Each release attaches a universal (Apple Silicon and Intel) `glint-iossim-macos` bridge with a sha256. glint downloads it on the first iOS attach when no local build exists, into `~/.glint/bin`. `GLINT_NO_BRIDGE_DOWNLOAD=true` turns that off.
- `GLINT_IOS_BRIDGE` points glint at a bridge binary.
- The bridge answers `glint-iossim version`, and glint warns when a local build speaks a different protocol.
- `attach` reports the input setup it is on (iOS runtime, Xcode, macOS and backend, or the Android API level) and whether glint has verified it, with known issues and the closest proven setup when it is untested. The list lives in `tested_matrix.dart`.
- `hittable` comes from Flutter's own hit test at the target's centre (`hitTest: "real"`); when that can't run it falls back to the old check and says `hitTest: "approximate"`. A miss names what would take the touch (`hitBy`), and a tap that would land on another widget is refused by default with `errorKind: notHittable` (#77).
- A glintId that is really a visible label ("Create account") gets a next step naming the id to use (#86).
- `scroll` reports `reason` when nothing moved: `atEnd`, `atStart`, `notScrollable` or `blocked` (#84).
- Buttons show `[selected]` when the widget (chips) or its `Semantics` wrapper says so, and a `Semantics` `checked`/`toggled` fills `[on]`/`[off]` for custom toggles. Selection counts as a change, so tapping a pill no longer reports `changed:false` (#78).
- Images name what they show (`- image profile.jpg (loaded)`), read from the image provider; a childless `CircleAvatar` or `Ink` is an image (#79).
- Action replies write the change report into their text (`· routeChanged`, `· nothing changed`) for clients that only read text (#78).
- Images sent to the model are shrunk and re-encoded first: by default JPEG at quality 75 with the longest side at 1024 px (`screenshotMaxSize`, `screenshotFormat`, `screenshotQuality` in `config`; `maxSize` per `device op:screenshot`). An iPhone 17 screenshot goes from a 1206×2622 PNG (about 2,900 tokens) to a 471×1024 JPEG (about 640). Every inline image says how its pixels map to `tap x,y` (#89).
- When native UI takes over, `get_scene` and the action reply attach the screenshot as an image instead of only a file path, and `record inline:true` attaches up to 4 frames at 512 px, so agents without a file tool can see them (#85).
- On Android, a system window in front of the app (the photo picker, another app) is detected from the window manager: the action reply says `changeCategory: nativeSurface` and names it, and `get_scene` lists the window's elements from `uiautomator dump` with `@ x,y` tap coordinates. When the dump fails it says why, for example when another automation tool holds the accessibility connection (#80).

### Fixed

- `telemetry op:"audit_verify"` reports entries written by two servers at once as a fork, not a broken chain, and new entries can't fork any more.
- `report_issue` now masks `access_token=` and `refresh_token=` values too. Redaction moved to glint_core, which uses the stricter of the two copies the packages had.
- A target clipped by its scroll view counted as painted and on screen, so taps landed on whatever covered it (on Android, the button bar below a form). It is now off-viewport, and the refusal says it is clipped or under the keyboard (#77).
- `scroll` swiped around the centre of the screen, which with the keyboard up is often the keyboard. It now swipes inside the visible part of the scrollable, above the keyboard (#84).
- Folded rows kept only their first text, so values on review and settings screens vanished (a row said "Distance" and hid "Up to 50 mi"). A folded item now keeps all its texts, and the trailer points at each run's parent to expand it (#82).
- Items in lazily built lists and wheels took their id from their slot, so after a scroll the same id meant a different item. Under ListView, GridView, ListWheelScrollView, CupertinoPicker and PageView, the id now follows the item's text; wheels and pickers also show as scrollable (#81).
- An empty Android recording said only "no frames captured". `record` now tells an empty recording from one that failed to decode, and on Android names the other tool's device server holding the screen (for example mobile-mcp's DeviceServer or scrcpy); the Android native reader does the same when `uiautomator` is killed (#95).
- A spinner inside a button didn't count as loading, so replies said `state: loaded` while the screen was still working. Loading is now read from every widget on the page. `wait_for_settle` no longer calls an animating screen settled while a spinner shows, and says which signal settled it (#83).
- A page route's own barrier and empty text-field chrome were read as open overlays, so errors claimed "a non-modal overlay is active" on plain screens (#86).
- Error replies showed only the first line of a VM error, which is often just "Unhandled exception:". They now include the line with the reason, and a failed geometry read is retried once and says what to do next (#87).
- iOS taps, keys and button presses were sometimes lost, and a key could repeat (typing `hello glint` gave `hello. glint`). The bridge sent each input message without waiting for the simulator to take it and could exit before the last one was delivered; it now waits for each message to be acknowledged, and fails with a clear error if one isn't.

### Changed

- A log value the VM can't expand now says how much was cut (`… [cut by the VM at 128 of 4000 chars]`) instead of silently showing the preview.
- Usage rollups come from glint_core. `telemetry op:"report"` also shows `avgEstimatedTokens`, `degraded` counts, and error kinds sorted by frequency.
- `attach` suggests `glint-network__network_attach` for HTTP monitoring, the network toolset's new name.

- On an Xcode major glint has not been verified on, bridge actions are refused with the new `errorKind: unsupportedToolchain` and steps to fix it; `GLINT_ALLOW_UNTESTED_XCODE=true` lets them run. A missing bridge now fails the same way instead of with a raw process error.

## [0.1.0] - 2026-09-25

First tagged release. glint lets an AI agent drive a running Flutter app on an iOS Simulator or Android emulator, with nothing added to the app.

### What it does

- `get_scene` reads the screen as a compact scene built from Flutter's own widget tree over the Dart VM service, with ids an agent can act on, and shows dialogs and sheets above the page they cover.
- Actions work like a person's: `tap`, `long_press`, `type`, `key`, `scroll`, `scroll_to_find`, `swipe`, `drag`, `hardware_button` and `batch`. Each reports whether and how the screen changed.
- `attach` with no arguments finds the running app and its device, and keeps working across a hot restart.
- Device mode drives a simulator or emulator without a Flutter app, through screenshots and coordinates.
- Also: app logs, screen recording, Face ID and Touch ID enrolment and matching on the iOS Simulator, and lock and unlock.

### Security and privacy

- Password fields show only their length, and typed text never reaches the action log or an issue report.
- `report_issue` drafts first and files only with the user's OK; paths, tokens, keys and passwords are redacted.
- Android typing sends text as one quoted argument, so shell characters are typed literally.
- Telemetry is off unless the user sets `GLINT_TELEMETRY=on`; see `TELEMETRY.md`.

### Known limits

See "Limits today" in the README: debug and profile builds only, Xcode 26 for iOS, ASCII typing, no web or desktop yet.
